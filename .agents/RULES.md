# Rules and operating boundaries

Permission to implement, test, format or organize does not authorize modifying protected content or expanding the task scope. These rules also apply to tools, scripts, generators and delegated agents.

## Scope

- Before writing, inspect Git status and identify the paths required for the task.
- Change only what is necessary to fulfill the request. Do not perform incidental refactoring, cleanup, dependency updates or reorganization.
- Preserve existing changes, including untracked files and staged changes. Do not overwrite, revert, move or delete others' work.
- Report problems outside the scope. Discovering a problem does not authorize fixing it.
- If the destination, ownership or write authorization is unclear, stop and ask the project owner.

## Protections

Read-only by default, including files and subdirectories:

- `.github/`: GitHub automation, governance and configuration, including `.github/ARCHITECTURE.md`, `.github/SECURITY.md` and `.github/CONTRIBUTING.md`.
- `.agents/`: agent rules, skills and configuration, including this file.
- `docs/`: project decisions and documentation.
- `infra/`: infrastructure and deployment.
- Any `AGENTS.md` in the repository.
- At the root: `PRODUCT.md`, `CONTEXT.md`, `DESIGN.md` and `GLOSSARY.md`, when present.
- Tool configuration, dependency manifests and lockfiles, including `package.json`, `bun.lock`, TypeScript, lint, formatting and hook configuration.

These paths identify protections, not reading instructions. Reading does not require write authorization. The root `README.md` and application and package READMEs may be edited within the task scope; a README inside a protected directory is not an exception.

Existing tests, pilots or experiments in protected directories do not authorize adding similar files, expanding those directories or automatically removing existing content.

## Authorization

Creating, editing, deleting, moving or renaming protected content requires an **explicit request and subsequent confirmation from the project owner**, after the AI presents:

1. The affected paths and intended operations.
2. The proposed changes and why they are necessary.
3. The expected effects, including files generated by commands.

Wait for confirmation before writing. The initial request is not confirmation. Do not infer authorization from generic requests such as “implement”, “fix the tests”, “organize” or “format”.

Authorization applies only to the presented scope. New paths or additional changes require fresh confirmation. Moving content into or out of protected directories also requires this procedure.

Do not bypass protections through symbolic links, indirect commands, generators or delegation. Permission to run tools does not authorize their writes to protected content.

## Directories and destinations

- `apps/`: applications and their composition.
- `packages/`: contracts, rules and reusable components.
- Application or package tests: use the structure already adopted by the component, such as `tests/` or `integration/`. Place tests next to source code only when that is the local convention.
- Root `tests/`: shared contracts and isolated integration scenarios between components, when required by the request.
- `docs/` and `infra/`: preserve their responsibilities and respect write authorization.
- `.agents/`: agent instructions, skills and configuration only. This is not a temporary workspace.
- `.github/`: not a location for application tests, benchmarks, tool pilots, reports, logs, caches or builds. A legitimate automation change or CI-specific test requires prior authorization and a previously presented destination.

Before creating a directory, look for a suitable existing destination. Do not create parallel structures, planned applications or generic experimentation directories on your own initiative. Do not impose reorganization or an artificial directory-depth limit on existing code.

## Temporary and generated files

- Use a task-specific system temporary directory outside the repository for exploratory scripts, disposable reproductions, benchmarks, logs and intermediate reports. Do not copy secrets or private inputs there.
- Normal tool artifacts must remain in their configured destinations, such as `dist/` and `coverage/`. Check write effects before running commands.
- Permanent tests and minimal fixtures belong to the component under test, not to the temporary directory or `.github/`.
- Do not version caches, builds, coverage, compilation metadata or intermediate results. Do not change `.gitignore` to hide improperly created files.
- When finished, remove only temporary files created by the task whose ownership is known. Never perform broad cleanup of ignored or untracked files.

## Formats and tools

This is a software repository, not a vault. Code, tests and configuration may use formats already adopted by the component; a list restricted to Markdown and PDF does not apply.

- Prefer Markdown for editable documentation.
- Reuse existing tools and dependencies. Do not install new tools, change manifests or lockfiles, or replace technologies without authorization for those paths.
- Do not create persistent helper files when a command or temporary file will suffice.
- Do not generate or add images, binaries or exports unless explicitly required by the task.
- Run relevant checks. Do not weaken rules, validation exclusions or testing requirements to obtain approval.
- Prefer checks that do not write files. Apply automatic fixes only to authorized paths; do not run repository-wide formatting or fixes that could change other files.

## Private inputs and destructive operations

- Keep original client inputs, private game files and local references read-only. Extractions and transformations require a separate, authorized destination.
- Do not expose credentials, keys, tokens, private Elex code or player data in code, fixtures, logs, reports or external services.
- Do not force-add ignored files or treat private local inputs as shared dependencies.
- Do not perform destructive cleanup, discard changes or rewrite history without specific authorization. This includes `git reset --hard`, `git clean` and restore operations that overwrite existing work.
- Testing does not authorize production access, sending messages, charging payments, deployment or mutation of real data. Use local resources or explicitly authorized test environments.

## References and delivery

- Use relative Markdown links for internal references; verify that the destination and section exist. Do not use Obsidian links.
- Do not invent URLs, test results or evidence. Distinguish executed verification, environment failures and hypotheses.
- Centralize reading instructions in `AGENTS.md`; do not create recursive chains of mandatory reading between documents.
- Before finishing, review the diff and Git status. Report changed paths, checks performed and outstanding limitations.
- Follow the contribution workflow for commits and delivery, including only task-related changes. A delivery requirement does not expand authorization to modify protected files.
